# Project Statement

## Project Title

**SmartSpend: Personal Expense Tracker and Budget Analyzer**

---

## 1. Problem Statement

Managing personal finances is a common challenge for students and individuals. People often spend money on food, travel, education, shopping, rent, entertainment, and other necessities without keeping a clear record. When income and expenses are not tracked properly, it becomes difficult to know the remaining balance, identify high-spending categories, and control unnecessary expenditure.

Traditional manual methods, such as notebooks or informal notes, are time-consuming and can lead to calculation mistakes, missing records, and difficulty in creating summaries. Users need a simple system that can record financial transactions, organize them into categories, compare expenses with budgets, and generate a clear financial report.

SmartSpend is proposed as a Java-based console application that solves this problem. The application enables a user to record income and expense transactions, define category-wise budgets, analyze spending patterns, generate financial summaries, export reports to a text file, and store data in an H2 database through JDBC.

---

## 2. Project Objective

The main objective of SmartSpend is to develop a simple, reliable, and user-friendly Java application for tracking personal financial activity.

The specific objectives are:

- To allow the user to record income transactions.
- To allow the user to record expense transactions.
- To classify expenses into meaningful categories.
- To store transaction data permanently using JDBC and H2 Database.
- To enable category-wise monthly budget setting and monitoring.
- To calculate total income, total expenses, and remaining financial balance.
- To identify the category in which the user spends the highest amount.
- To display budget warnings when expenses exceed the configured limit.
- To generate and export a monthly financial report using Java I/O streams.
- To demonstrate important Java programming concepts in a real-world use case.

---

## 3. Scope of the Project

SmartSpend is designed as a single-user, offline, console-based personal finance management prototype.

The project includes:

- Income and expense entry.
- Category selection using predefined Java enum values.
- Transaction storage and retrieval.
- Transaction deletion.
- Budget creation and budget update.
- Category-wise spending analysis.
- Budget comparison and exceeded-budget warnings.
- Financial report generation.
- Text-file export of the report.
- Persistent storage using H2 embedded database and JDBC.

The project does not include:

- Multi-user login or authentication.
- Online banking integration.
- Credit/debit card integration.
- Real payment processing.
- Cloud synchronization.
- Mobile application support.
- Graphical user interface.
- Real email or SMS alerts.

These features are proposed as future enhancements.

## 7. Non-Functional Requirements

### NFR-01: Usability

The system shall provide a simple menu-driven interface. Each menu option shall be numbered, and the application shall display clear prompts, confirmations, and error messages so that a beginner can use it without technical training.

### NFR-02: Reliability

The system shall validate input data and handle exceptional situations safely. Invalid amounts, invalid menu selections, incorrect numeric values, unavailable transaction IDs, invalid dates, and database errors shall be handled using validation and exception handling.

### NFR-03: Maintainability

The application shall use a modular package structure. Model classes, service classes, repository classes, utility classes, and custom exception classes shall be placed in separate packages. This makes the code easier to read, test, debug, and extend.

### NFR-04: Performance

The system shall retrieve stored records through JDBC queries and use Java collections for category-wise aggregation. For the scale of a single-user expense tracker, response time should remain fast for normal transaction volumes.

### NFR-05: Data Integrity

The system shall prevent invalid data from being stored. Transaction amounts and budget limits must be greater than zero. Transaction categories must be selected from the predefined `Category` enum. The database schema shall use primary keys and a unique category field in the budgets table.

### NFR-06: Resource Efficiency

Database connections, SQL statements, result sets, file writers, and readers shall be closed after use to avoid unnecessary resource consumption.

### NFR-07: Portability

The application shall run locally through BlueJ on a system with Java and the H2 Database JAR installed. The embedded H2 database removes the need for a separate database server installation.

### NFR-08: Error Handling Strategy

The system shall use custom exceptions, such as `InvalidAmountException`, and Java exception handling blocks (`try`, `catch`, `throw`, and `throws`) to prevent unexpected program termination and provide meaningful messages to the user.

## 10. Data Storage Design

The project uses H2 embedded database through JDBC.

### Table: `transactions`

| Field | Data type | Constraint | Purpose |
|---|---|---|---|
| `id` | INT | Primary key, identity | Unique transaction ID |
| `transaction_type` | VARCHAR(20) | Not null | Specifies INCOME or EXPENSE |
| `category` | VARCHAR(50) | Not null | Transaction category |
| `amount` | DECIMAL(12,2) | Not null | Transaction amount |
| `description` | VARCHAR(255) | Optional | Transaction note/details |
| `transaction_date` | DATE | Not null | Date of transaction |

### Table: `budgets`

| Field | Data type | Constraint | Purpose |
|---|---|---|---|
| `id` | INT | Primary key, identity | Unique budget ID |
| `category` | VARCHAR(50) | Unique, not null | Expense category |
| `monthly_limit` | DECIMAL(12,2) | Not null | Maximum allowed monthly spending |

## 11. Design Decisions and Rationale

### Console-based design

A console interface was selected because it is simple, fast to develop, easy to demonstrate in BlueJ, and appropriate for demonstrating core Java concepts within the project timeline.

### Abstract `Transaction` class

`Transaction` is designed as an abstract class because income and expense share common properties such as ID, category, amount, description, and date. However, their meanings differ: income increases balance while expense decreases balance.

### Inheritance and polymorphism

`Income` and `Expense` inherit from `Transaction`. They override methods such as `getType()` and `getSignedAmount()`. This avoids duplicate code and demonstrates Java inheritance and runtime polymorphism.

### Enum for categories

The `Category` enum ensures users select only predefined valid categories. This improves data consistency and reduces invalid category values.

### Repository pattern

A `TransactionRepository` interface separates database operations from business logic. `JdbcTransactionRepository` implements the interface using JDBC. This makes the design modular and makes it easier to replace JDBC with JPA in the future.

### H2 embedded database

H2 Database was chosen because it is lightweight, Java-based, supports JDBC, and can run locally without requiring separate MySQL server installation.

### File-based report export

A formatted report is exported to a `.txt` file using Java I/O streams. This provides a persistent report that can be opened without the application.
